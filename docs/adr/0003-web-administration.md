# ADR 0003: 端末内HTTPサーバーによるWebからの管理

## 決定

端末の管理画面で有効にした場合だけ，固定ポート47623でHTTPを待ち受ける．同じネットワークのブラウザにはIPアドレスのURLとQRコードを渡す．iPadの外部展示中・停止中は，本体にもQRコードを表示する．外部画面には出さない．Bonjourで公開しない．既定は無効とし，この設定を含まない旧Profileも無効として読む．

端末の管理者パスワードを共用する．Administrationが検証結果，失敗回数と30秒の待ち時間を裁定する．Webからの失敗を重ねると端末での解除も待ち時間に入る．これは遠隔から端末の解除を一時的に妨げられることを意味する．HTTPは通信を暗号化しないため，展示用ネットワークを他の用途から分けて運用する．

Rootが同時に1つのセッションを所有する．32バイトの乱数をブラウザのページ内メモリだけに保持し，API要求のAuthorizationヘッダーで送る．CookieとURLには入れない．無操作15分，発行から8時間で失効する．状態を定期的に読む通信では無操作の期限を延ばさず，編集・保存などの操作で延ばす．編集中も認証状態を確認し，入力値の表示は更新しない．接続が戻ったら通信エラーの表示を消す．失効したらログイン画面へ戻し，古いセッションへの遅い応答や通信エラーで新しいログインを変えない．新しいログインは古いセッションを置き換える．管理者パスワードを変更した場合は，既存のセッションと検証中のWebログインを破棄する．Webからの管理を無効にすると，待ち受けとセッションを破棄する．

すべての要求でHostを端末自身のIPアドレスと待ち受けポートに限定する．状態を変えるPOSTには，同じURLのOriginを必須とし，Originがない要求と `null` を拒否する．CORSの許可ヘッダーは返さない．未認証のページとAPIから保存済み設定・資格情報を返さない．展示用WebViewの画面遷移では，ループバックと端末自身の管理サーバーのoriginを拒否する．

Webの要求はRoot配下のWebAdministration Nodeから親方向のCoRへ送る．認証結果はAdministration，セッションとサーバーの寿命はRootが裁定する．表示に渡す値はPresenterが保存済みProfileとRootの状態から作る．端末の設定画面のPropsには入力中の管理者パスワードがあるため流用しない．

## 設定と展示の操作

Webと端末はAdministrationの同じdraftと検証・保存経路を使う．Webで編集した下書きは，端末で管理画面を開いても保持する．破棄操作か保存によって更新する．Webから編集できるのは開始URL，閲覧先，入力，無操作復帰，展示先と出力設定である．管理者パスワード，生体認証，Webからの管理の有効状態は端末でだけ変更する．出力先と解像度は端末の接続状態から得た選択肢に限定し，外部用ウィンドウの準備は端末で行う．管理中のWeb画面からも，保存済み設定で展示を開始できる．開始は端末と同じRootの条件を通し，未保存の変更や利用できない展示先があれば拒否する．

展示中にもWebから保存できる．保存後もactiveProfileを保ち，展示中のページと閲覧先のルールを変えない．「やり直す」はRootがLeavingKioskからAdministrationを経ずにEnteringKioskへ進め，保存済みの設定で始める．未保存のdraft，解除中，展示の開始・終了中，SafeHoldではやり直しを拒否する．

Webから展示を止めるとRootはPausedになり，展示用Webを止めて停止中の画面を保つ．Webからの再開は保存済み設定で始める．障害によるSafeHoldからも，開始条件を満たす場合に再開できる．Webの操作だけで端末の管理画面へ進めない．端末の管理画面を開くには，停止中も端末で管理者認証する．Pausedは保存せず，アプリの再起動時には保存済み設定で展示を始める．

## 待ち受けの寿命

iPadとiPhoneではアプリが背景に移るとRootのEffectで待ち受けと接続を止め，前景復帰時に同じポートで新しいlistenerを作る．背景中に保存や起動処理が完了しても待ち受けを始めない．Macではスリープから戻ると同じ手順で作り直す．前のlistenerの取消完了を待ってから同じポートで開始し，その間に起動が取り消された場合は待ち受けを作らない．起動後にlistenerが失敗した場合はURLを消してエラーを表示する．有効期限内のセッションは保持する．

ネットワークの変更時には使用中のインターフェースからアドレスを読み直し，端末の管理画面とiPad本体のQRコードを更新する．IPv6だけのネットワークではIPv6形式のURLを出す．ブラウザは通信断を表示し，保存要求の応答がなければ保存結果が不明なことを示す．再接続後は端末の最新状態を読み直す．

## 理由

初回接続するスマートフォンへ信頼済みのHTTPS証明書を配る手順は，QRコードで開く展示端末の運用に合わない．Appleの[ローカルネットワークTLS資料](https://developer.apple.com/documentation/network/creating-an-identity-for-local-network-tls)にある自前の認証局を使う方式では，接続する端末すべてにルート証明書の導入が必要になる．HTTPの危険を運用上のネットワーク分離と，Host・Origin・認証・セッションの制限で抑える．同じネットワークの盗聴者にはパスワードとセッションを読まれ得るため，これらの制限で暗号化の代わりにはならない．

Cookieを使わず，セッションをページ内メモリだけに置くと，別サイトからブラウザに要求を送らせても認証情報が自動では付かない．さらにHost検査でDNS rebindingを，Origin検査で別サイトからの状態変更を拒否する．APIの応答は `no-store` とし，画面へ入る値はHTMLではなく `textContent` で挿入する．

展示中の保存を許すのは，端末の管理画面を出さずに設定を変更するためである．保存と反映を分けることで，変更途中のルールやURLが来場者の展示へ突然入ることを防ぐ．PausedをSafeHoldと分けるのは，管理者が止めた場合と障害で止まった場合を端末・ブラウザの両方で区別するためである．

[AppleのTN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)では，着信TCPの待ち受けと受け入れにローカルネットワーク許可は不要で，Bonjourには許可が必要とされる．Mac App Store向けのSandboxビルドには `com.apple.security.network.server` を付ける．

## 確認範囲

Coreの認証・セッション・展示状態の試験，実TCPでのHost・Origin・未認証要求と同じポートでの再開始，実WebKitでの管理サーバーへの遷移拒否を実行した．ヘッドレスブラウザではログイン，展示中の保存・やり直し・停止・再開を操作した．配布ビルドと実機のローカルネットワーク許可・ファイアウォール表示，端末のスリープとWi-Fi切替は別途実機で確認する．
