# iPad対応の方針

iPad版では，本体と外部ディスプレイのどちらも展示先にできる構成にする．展示にはマウス操作が必要．Core・Presenterと所有・配送の仕組みを共用し，UIKit，入力，画面の寿命，端末の制限はiPad用Adapterで扱う．汎用ブラウザや配信CMSへの拡張は行わない．

本体の展示・管理・認証はUIKitで実装し，iPad／iPhone SimulatorとiPhone実機で通しUI試験が成功した．PackageはmacOS 14とiOS 18.4以降を指定する．外部表示専用Sceneと，対応端末の対話可能な展示ウィンドウを実装した．外部表示専用Sceneの表示・本体からのクリック・解除取消・再開始はiPad Simulatorで確認した．iPadOS 26.6.2の実機でも外部映像接続・本体からのリンク・スクロール・ドラッグ・動画・解除と再開を確認した．解像度の選択と全4方向の回転を実装し，試験した接続では自動選択の1920×1200で正円と黒帯なしを確認した．トラックパッドの接続・マウス固定・外部カーソルの描画は確認済みだが，物理入力によるWeb操作・画面端での制限と端末の管理方式は未確認．外部Sceneが接続済みなら追加のウィンドウ作成ボタンを表示しない．Apple資料とSDKの調査結果は [外部ディスプレイと端末制限](../references/ipad-external-display.md) に記録する．

## 展示先と画面モード

展示先と，展示・認証・管理のモードを別の値として扱う．本体の画面だけを切り替えてRootの状態と異なる管理画面を開く実装はしない．

| 展示先 | 本体の役割 | 外部ディスプレイの役割 |
| --- | --- | --- |
| 本体 | 展示Viewと，認証を経て開く管理Viewを切り替える | 接続を開始条件にしない．接続時に管理情報がミラーリングされる問題は別途確認する |
| 外部ディスプレイ | 管理者入口・認証・管理操作を置く | 外部画面の比率で独立した展示Viewを表示する．対話可能なウィンドウでは直接操作し，表示専用Sceneでは本体の操作面から操作する |

展示先の変更は管理画面のdraftで行い，保存した値を次の展示開始時に固定する．展示中のViewの再構築や接続通知だけで展示先を変更しない．本体を選んだ場合は外部画面がなくても開始できる．外部を選んだ場合は，その展示に必要なSceneと入力が利用可能であることを開始条件にする．

外部展示では，Webの表示領域を外部Sceneの幅・高さに合わせる．本体の画面を複製するミラーリングは採用しない．本体と外部の比率の違いによって黒帯が出る方式では，今回の外部展示の目的を満たさない．これは製品要件であり，Webコンテンツ自体の画像・動画の比率を強制的に変更する要件ではない．外部表示専用Sceneでは対応する解像度を一覧から選択・保存する．初期値はOSの選択とし，公開APIがパネルの物理解像度を特定できない場合も同じ扱いとする．

外部画面を切断した場合，本体へ展示を自動で移さない．対象のWeb世代と入力を無効化して停止する．再接続時にはSceneの識別子と世代を更新し，旧画面からの完了・入力を受け入れない．

外部出力の回転は0度・右90度・180度・左90度から選んで保存する．90度・270度ではWebの表示領域の幅と高さを入れ替える．Webとカーソルを一緒に回転し，本体の向きと独立させる．実装と検証範囲は [縦置き](mobile-external-output.md#縦置き) を参照する．

## マウス入力と端末の制限

外部展示ではアクセスガイドを運用の前提にしない．これは運用条件であり，全機種・全OSで外部表示との併用が不可能だと検証した結論ではない．Single App Mode／Autonomous Single App Modeも，外部表示の問題を解消すると確認するまでは採用を確定しない．

外部の表示専用Sceneは，通常のWKWebViewを外部画面で直接マウス操作する要件の完成解とはしない．対話可能なウィンドウを使う場合も，全画面表示と，本体側へカーソルが移らないことは別に検証する．

UIKitのポインタロックは，システムカーソルを隠して全画面のアプリへマウス入力を限定する仕組み．ロックの要求は必ずしも認められず，Sceneの実際の状態を確認する必要がある．ゲーム向けの相対入力と，通常のWebの位置指定クリックを同じ契約とは扱わない．WKWebViewのリンク・フォーム・hover・スクロールを保ったまま利用できるかは未確認．[Appleのポインタロック資料](https://developer.apple.com/documentation/uikit/uipointerlockstate)，[入力の解説](https://developer.apple.com/videos/play/wwdc2020/10617/)

ポインタロック，タッチによるOS操作，端末を1アプリへ固定する制限は別の条件として検証する．一時的なアプリ切替では展示を停止し，Plinthが前面へ戻ると画面の準備とマウス固定をやり直して再開する．管理者解除や外部画面の切断後には自動再開しない．詳しくは [外部表示](mobile-external-output.md#本体操作) を参照する．

カーソル制限の代わりにミラーリングへ変更して，外部展示の要件を満たしたとは扱わない．外部画面の比率に合う独立した表示と，通常のWeb操作，カーソルの画面間移動の制限を同時に検証する．

## ショートカットからの展示リセット

iPad・iPhoneのショートカットに「展示をリセット」を用意する．手動実行と時刻のオートメーションは同じ操作を使う．引数は設けず，展示を開始したときの設定にある復帰モードと開始URLを使う．ショートカットからの要求はRootへ送り，展示中でWebへの入力を受け付けられるとき，または展示からアプリを切り替えて前面復帰を待っているときに受理する．展示前，展示停止後，同じ復帰中の重複要求は拒否する．

受理後は入力を止め，旧WebViewの解放を確認してから新しいWebViewを作り，開始URLを読み込む．ショートカットへ返す「開始しました」は要求の受理を表し，ページの読み込み完了を表さない．リセットによって認証画面や管理画面を開かず，展示先も変更しない．

ショートカットの実行時にOSがPlinthを前面へ戻す場合は，通常のアプリ復帰と同じ状態遷移を経る．展示からアプリを切り替えたために復帰を待っている間は，最初のリセット要求をその復帰に合流させ，同じ復帰中の重複要求は拒否する．復帰処理が新しいWebViewを復帰モードに従って作り，開始URLを読み込む．時刻のオートメーションでは，OSが操作を発火させたことと，展示が開始URLへ戻ったことを別々に確認する．

## 共用する範囲と追加する境界

| 領域 | 方針 |
| --- | --- |
| Core・Presenter | URL Policy，設定値，認証，保存，復帰，Propsへの投影を共用する |
| 所有ツリー・同期配送・Task／reply管理 | `KioskRuntime` に共用する．Nodeの所有と親方向CoRは変えない |
| Native View・画面の寿命 | UIKit／SwiftUIのiPad用ViewとAdapterを置く．表示先別のSceneの接続・非アクティブ化・復帰を型付きFactでRootへ送る |
| WebSurface | WKWebViewのnavigation契約を共用し，Viewへの取り付けと入力はOS別にする |
| Presentation・入力 | Macの画面数・マウス・キーボード前提を，iPadの表示条件・タッチ操作と区別する |

`KioskProfile.exhibitionDestination` は本体と外部を区別する．旧JSONで項目がない場合は本体として読む．RootはmobileDisplaysの本体・外部の利用可能状態で開始を裁定する．Macは別の画面選択契約を使う．表示専用Sceneは `.windowExternalDisplayNonInteractive` で接続し，iOS 27ではSceneAccessoryに登録する．対話可能な追加Sceneは対応端末だけで `.windowApplication` として作成し，操作者が外部へ移す．外部画面上で全画面となったSceneだけを利用可能と通知する．作成要求の送信だけで完了扱いにせず，接続・継続activity・エラーをoperationと照合する．

## 管理者解除と制限の所有

アプリ内の管理者認証と，OSが他のアプリへの移動を制限する状態は別に管理する．OSや管理ツールが所有する制限を，アプリの管理者パスワード認証だけで解除できるとは扱わない．管理画面は制限が続いていても同じアプリ内で開けるようにする．

Autonomous Single App Modeを使う場合は，Rootが選んだEffectだけで開始・終了を要求する．APIの完了結果と現在の状態を確認し，要求を送っただけで取得成功としない．取消後の完了もoperation tokenで照合し，取得した制限の解放を取りこぼさない．

iPadには物理キーボードを前提としない管理者入口を設ける．入口の操作は解除の認証を省略する根拠にならない．Rootが認証成功を受けて管理へ遷移し，ViewはPropsを描画するだけとする．生体認証を選んだ場合，OSの認証画面は解除中に限って本体の画面に出し，外部の展示画面には出さない．現在のCoreは，認証成功後に展示を停止してから管理を開く契約．管理中も外部展示を続ける場合は，状態機械・Effect・保存後の反映を追加設計する．

管理Viewと認証情報を外部へ誤表示しないことを条件にする．単にViewを分けただけでこの条件を満たしたとはしない．通常のミラーリング，Sceneの接続前後，モーダル表示での外部Sceneやポインタロックの解除を実機で確認する．

生体認証を有効にした端末では，解除画面のボタンを押したときだけ，端末本体にFace IDまたはTouch IDのOS認証画面を出す．解除画面を開いただけでは始めない．外部画面には展示だけを出し，認証画面や管理情報を出さない．失敗・取消・登録変更・60秒経過の後も管理者パスワードで解除できる状態を保つ．

## 実装と検証の条件

1. 外部画面の比率に合う独立した全画面表示・カーソル制限・通常Web操作を最小の実機検証で確認する．成立しない方式を製品の前提にしない．
2. 共通RuntimeとOS別targetを分け，iPadのdeployment targetとisolationを実際のSDKで確認する．Xcode 27.0／SDK 27.0でiOS 18.4を下限とするビルドが成功した．26以降はeffectiveGeometryを使い，古いOSでは従来のcoordinateSpaceと通知を使う．18.4系の実行確認は残る．
3. 展示先の設定，Rootの表示条件，OS制限の所有契約を実装し，対応するPresenterと回帰試験をそろえる．
4. iPad用View・入力・WebKit・資格情報保存を結合する．Coreの回帰試験は両OSで共用し，NativeのUI試験はOS別にする．
5. 実機で本体・外部の展示，管理への切替，接続変更，バックグラウンド復帰，制限の解除失敗を確認する．Simulatorやfake Portでは端末の制限を証明しない．

macOS版の仕様は [設計書v0.2](macos-kiosk-design-v0.2.md)，現在の実装範囲は [開発と検証](../development.md) を参照する．
